\begin{abstract}
Data centers and server halls require continuous visibility into thermal, airflow, humidity, and fire-related conditions to prevent thermal runaway, equipment damage, and costly unplanned downtime. This report presents \emph{ThermoSentinel}, a full-stack edge--fog--cloud system that models facility-wide telemetry from heterogeneous sensors through a local fog aggregation tier into a serverless cloud API, with a browser dashboard for rack-level situational awareness and risk scoring. The default developer path uses HTTP from a sensor simulator to a fog node, then HTTP ingest into a Next.js API (local) or AWS Lambda (deployed); an optional path uses MQTT via AWS IoT Core. Production deployment combines AWS Amplify Hosting for the static web UI, Amazon API Gateway (HTTP API) with AWS Lambda, Amazon DynamoDB for readings, optional Amazon SQS for decoupled ingest, Amazon SNS for critical alerts, and optional Turso (libSQL) for alternate persistence. We summarize objectives aligned with operational resilience and cost avoidance, the end-to-end data flow, architectural rationale, implementation components, deployment practice, and reflective lessons from integration across edge, fog, and cloud.
\end{abstract}

\section{Introduction}

\subsection{Domain and motivation}
Modern data centers must maintain tight environmental envelopes: excessive heat raises failure rates and energy use; low humidity invites electrostatic risk; high humidity risks condensation; restricted airflow and smoke precursors can precede equipment loss or safety incidents~\cite{buyya2016fog}. Unplanned outages and thermal emergencies carry large operational and reputational costs; early detection and unified telemetry reduce mean time to detect and support capacity decisions~\cite{armbrust2010cloud}.

ThermoSentinel targets this domain: it models a multi-rack facility where simulated or real sensors feed a \emph{fog} node for validation and batching, then a \emph{cloud} ingest and query API, with a dashboard that highlights aggregates, trends, and simple risk metrics so operators can act before conditions become disasters.

\subsection{Objectives}
The project objectives are:
\begin{itemize}
  \item Provide an \textbf{edge--fog--cloud} pipeline from sensors to durable or queryable cloud state, with a clear mapping from each software component to the physical narrative (sensors $\rightarrow$ fog $\rightarrow$ cloud $\rightarrow$ operators).
  \item Deliver a \textbf{responsive web application} with rack views, metric cards, trend charts, analytics views, architecture documentation, and optional scenario toggles for stress narratives.
  \item Deploy a \textbf{cloud API} on AWS using API Gateway and Lambda, with infrastructure-as-code and environment-driven configuration.
  \item Minimize \textbf{recurring hosting cost} for teaching and demo workloads by using static frontends and pay-per-request backends~\cite{baldini2017serverless}.
\end{itemize}

\subsection{Requirements}
\textbf{Functional:} (R1)~accept structured ingest envelopes at the cloud; (R2)~query recent time-ordered readings per sensor type; (R3)~health and fog-status visibility; (R4)~dashboard refresh compatible with static hosting and CORS; (R5)~configurable simulator and fog timing; (R6)~optional MQTT path via AWS IoT Core~\cite{aws2024iot}. \textbf{Non-functional:} modular TypeScript services; separation of UI and API for Amplify; optional DynamoDB and SNS in the deployed stack~\cite{amazon2024lambda}; reproducible builds and documented environment variables.

\section{Architecture and Design}

\subsection{End-to-end project flow}
The \textbf{exact logical flow} implemented in the repository is as follows (HTTP is the default local path; MQTT is optional).

\textbf{Local development (\texttt{npm run dev}, same as \texttt{npm run dev:all}):}
\begin{enumerate}
  \item \textbf{Sensor simulator} (Node.js, TypeScript) generates readings for temperature, humidity, pressure, airflow, and smoke at per-type sample and dispatch intervals; by default it uses \textbf{HTTP} \texttt{POST} to the fog ingest endpoint \texttt{http://localhost:4000/ingest} (configurable \texttt{FOG\_URL}).
  \item \textbf{Fog node} (Node.js HTTP server on \texttt{FOG\_PORT}, default \texttt{4000}) validates payloads, batches readings, optionally forwards to Amazon SQS, and \texttt{POST}s envelopes to \texttt{CLOUD\_URL}, default \texttt{http://localhost:3000/api/ingest}.
  \item \textbf{Next.js} (App Router) serves the dashboard and API routes under \texttt{/api/*}; ingest processing stores readings (in-memory in dev, or DynamoDB/Turso when configured) and exposes \texttt{GET /api/sensors/\{type\}/readings}.
  \item The \textbf{browser} polls REST endpoints (and \texttt{/api/fog/status}, which proxies fog \texttt{GET /status} on port 4000) to render cards, racks, and charts.
\end{enumerate}

\textbf{Optional MQTT / AWS IoT path (\texttt{npm run dev:iot}):} the simulator publishes to AWS IoT Core (\texttt{mqtts://}, port 8883); the fog node subscribes with a topic filter, then the same cloud dispatch applies~\cite{mqtt2014,aws2024iot}.

\textbf{Deployed cloud path:} the static dashboard on \textbf{AWS Amplify} calls \textbf{Amazon API Gateway} (HTTP API) $\rightarrow$ \textbf{AWS Lambda} $\rightarrow$ \textbf{Amazon DynamoDB} (readings table); optional \textbf{Amazon SQS} receives duplicate batches from the fog for asynchronous processing; \textbf{Amazon SNS} can notify operators on critical thresholds. The UI is built with \texttt{STATIC\_EXPORT=true} so \texttt{app/api} routes are disabled in the export bundle; the browser uses \texttt{NEXT\_PUBLIC\_LAMBDA\_API\_URL} (and optionally \texttt{NEXT\_PUBLIC\_LOCAL\_API\_URL} for HTTPS tunnels to a developer PC).

\subsection{Layered architecture and justification}
The three tiers follow established fog/edge practice~\cite{vaquero2014research,yi2015survey}: \textbf{edge} (sensors or simulator), \textbf{fog} (protocol bridging, validation, batching), \textbf{cloud} (durable storage, scalable API, alerting). Splitting the \textbf{static UI} (Amplify + CDN) from the \textbf{API} (API Gateway + Lambda) avoids always-on web servers, contains blast radius, and matches variable demo traffic~\cite{amazon2024apigw}. DynamoDB provides a managed store aligned with Lambda; SQS decouples ingest spikes; SNS supports email or downstream automation for critical events.

\subsection{Design patterns}
Patterns used include: \textbf{single HTTP API entry} via API Gateway; \textbf{multiplexed Lambda handler} for health, ingest, and readings; \textbf{shared TypeScript libraries} between Next.js API routes (local) and Lambda (production); \textbf{CORS} for browser access from Amplify origins; \textbf{environment-based API base resolution} (\texttt{publicApiUrl}) for local vs.\ Lambda modes; \textbf{fog status proxy} so the dashboard does not call the fog origin directly when unnecessary.

\subsection{Risk scoring (illustrative)}
Per-sensor status is derived from temperature and humidity bands in the UI; a simple capped aggregate risk score $R$ is computed as in~\eqref{eq:risk}, guiding operator attention without replacing facility-specific runbooks.
\begin{equation}
R = \min\bigl(100,\; 15\,n_w + 40\,n_c\bigr),
\label{eq:risk}
\end{equation}
where $n_w$ and $n_c$ are counts of sensors in warning and critical states respectively.

\subsection{Application features (operator-facing)}
The web application provides: \textbf{data source toggle} (same-origin local API vs.\ deployed Lambda URL); \textbf{system and fog pipeline status}; \textbf{aggregate metric cards} (temperature, humidity, pressure, airflow, smoke); \textbf{rack-level views} with per-server status; \textbf{temperature trends and backend analytics panels}; \textbf{architecture page} summarizing topology; \textbf{simulation toggles} for narrative demos (e.g., thermal stress). Together these support the project motto: \emph{monitor the data hall continuously, surface anomalies early, and reduce the risk of costly downtime and thermal incidents} by maintaining the best achievable environmental envelope given the sensor footprint.

\subsection{Limitations and security posture}
The codebase prioritizes reproducibility for coursework: authentication on ingest may be absent; CORS can be permissive for integration. Production hardening would add mutual TLS or tokens fog-to-cloud, API keys or OAuth for reads, rate limits, AWS WAF in front of API Gateway, and private networking as needed~\cite{owasp2023api}.

\section{Conclusions}

ThermoSentinel demonstrates a traceable path from edge telemetry through fog aggregation to a serverless AWS backend and a modern static web frontend. Principal findings: (1)~separating Amplify-hosted UI from the Lambda API matches static hosting and global edge caching while keeping API evolution independent; (2)~HTTP-first local development lowers the barrier before introducing MQTT and IoT certificates; (3)~DynamoDB and SNS integrate naturally with Lambda for durable reads and operator notifications; (4)~explicit sensor timing and fog batching illustrate bandwidth--latency trade-offs relevant to real halls~\cite{yi2015survey}.

\subsection{Reflection}
Building the system highlighted that \textbf{deployment details}---static export constraints, mixed-content rules for HTTPS dashboards calling loopback APIs, CORS, \texttt{FOG\_PORT} vs.\ generic \texttt{PORT}, and publishing all \texttt{\_next/static} assets---are as consequential as core monitoring logic. Early use of environment-driven API bases and documented stacks reduced integration friction when moving from laptop to Amplify. A worthwhile next step would be automated smoke tests against deployed API and dashboard asset URLs in CI.
